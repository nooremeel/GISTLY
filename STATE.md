## Key Architectural Decisions
- **AI Provider:** Google Gemini API, accessed via its official SDK from the backend only (never exposed to frontend).
- **AI Model Choice:** Using `gemini-3.5-flash-lite` — the free tier caps full Flash models (`gemini-3.5-flash`, `gemini-3.6-flash`, `gemini-2.5-flash`) at 20 requests/day, unusable for dev iteration, while Flash-Lite gives 500/day and 15 RPM. Flash-Lite is also the right fit for the task itself (short extraction/classification, not long-form reasoning), not just the cheaper option (Task 07).
- **AI Failure Handling:** `aiService.generateSummaryAndTags` never throws — on any Gemini error, malformed response, or fetch failure it returns `{ summary: null, tags: [] }` so bookmark creation always succeeds even if the AI call fails, times out, or the source page can't be fetched (Task 07). Task 08 confirmed this path also covers rate-limit/timeout cases without additional code. **Relevant for Task 17:** since the backend never throws on AI failure, `AddBookmarkForm.jsx`'s loading state only needs to cover normal request latency (including AI call time), not a distinct AI-failure branch — a bookmark with `summary: null, tags: []` is still a 200/201 success response.
- **Bookmark Content Source for AI:** Priority order is fetched page text (via `urlFetcher.fetchPageText`) → user-submitted `note` → raw `url` string as a last resort. Page fetches are capped at 6 seconds and 6000 characters to bound latency and token cost (Task 07). **Relevant for Task 17:** the AI call (plus optional page fetch) means `POST /api/bookmarks` can take several seconds — the loading state in `AddBookmarkForm.jsx` should assume multi-second latency, not treat it as a fast local operation.
- **Tag Merging:** `createBookmark` merges user-submitted tags with AI-generated tags rather than one overriding the other, deduped case-insensitively with user-typed casing taking priority on collision. Near-duplicate tags that aren't exact string matches (e.g. "Node.js" vs "NodeJS") are NOT currently caught — deferred, see Open Questions (Task 07).
- **Database:** MongoDB with Mongoose for schema/validation. Bookmark schema indexes `user` and compound-indexes `{ user, tags }` for aggregation performance — this is the index `getGrouped`/`getByTag`'s aggregation pipelines rely on (Task 09).
- **DB Connection Pattern:** `backend/config/db.js` exports a single async `connectDB()` function, called once at server bootstrap in `server.js`; connection failure exits the process rather than allowing the server to start in a broken state.
- **Auth (Backend):** JWT-based sessions. Token issued on login, stored in an httpOnly, `SameSite=Lax` cookie (not localStorage) to reduce XSS exposure. Passwords hashed with `bcryptjs`, salt rounds ≥10. Token expiry set to 7 days. Cookie/JWT logic centralized in `backend/utils/generateToken.js` (`generateToken`, `setTokenCookie`, `clearTokenCookie`) rather than duplicated per-route.
- **Password Field Handling:** `User.password` uses `select: false` in the schema so it's excluded from query results by default; `authController.login` explicitly opts in with `.select('+password')` only where needed.
- **Authorization Pattern:** Every bookmark query filters by ownership in a single combined Mongo filter (e.g. `{ _id, user: req.user.id }`), set via `auth.js` middleware — no bookmark route is ever unprotected, and no route queries `Bookmark` without that scope. Task 09's aggregation routes scope their `$match` stage by `user: req.user.id` (manually cast to `ObjectId`) for the same reason.
- **Not-Found vs Forbidden:** Bookmark routes return `404` (not `403`) for both "doesn't exist" and "exists but belongs to another user," and also for malformed ObjectId `CastError`s — all three cases are indistinguishable to the caller, preventing existence/ownership leaks (Task 06). As of Task 15, the frontend now actively distinguishes these 404s in the UI (via the `apiClient` `.status` fix) to show "already deleted"-style messaging.
- **Mongoose Hook Style:** `pre('validate')`/`pre('save')` hooks are written as `async function () {...}` with no `next` parameter — never mix an `async` hook signature with an explicit `next()` call, since Mongoose only supplies `next` to non-async hooks and calling it on an async hook throws `TypeError: next is not a function` (Task 06 deviation, fixing the Task 05 hook).
- **Mutating Updates Use `.save()`:** `updateBookmark` fetches the document then calls `.save()` rather than `findOneAndUpdate`, so schema-level `pre('validate')` hooks (e.g. the url/note cross-field rule) still run on edits, not just on creation. This is the pattern Task 15's `EditBookmarkModal.jsx` relies on via `PUT /api/bookmarks/:id`.
- **Security Middleware:** `helmet` for headers, `morgan` for request logging, and a custom in-place sanitizer (see Task 03 deviation) against NoSQL injection — all applied at server bootstrap (Task 03), before any feature routes exist.
- **CORS:** Configured early for local dev (`CLIENT_ORIGIN`, `credentials: true`), locked to the production frontend origin only at deploy time (Task 18).
- **Rate Limiting:** Implemented in Task 08. `authLimiter` (15 min / max 10 / only failed attempts count) applied to `POST /api/auth/login`; `aiLimiter` (1 hour / max 20) applied to `POST /api/bookmarks` only. Both wired as exact-path `app.post(...)` middleware in `server.js` (now `app.js` as of Task 10), registered before the corresponding router mount, rather than inside `routes/auth.js`/`routes/bookmarks.js`. **Relevant for Task 17:** `AddBookmarkForm.jsx` should handle a 429 response from `aiLimiter` (20 creations/hour) with a specific toast message via `err.status === 429`, consistent with the Task 15 `err.status` convention, rather than a generic failure message.
- **Error Handling (Backend):** Centralized in `backend/middleware/errorHandler.js` (Task 08) — `notFound` + `errorHandler`, mounted last in `app.js`. Existing Task 06/07/09 controllers still catch and respond locally per-handler (not refactored to `next(err)`); `errorHandler.js` currently acts as a safety net for anything uncaught or thrown outside those try/catch blocks, not the primary path yet.
- **Input Validation:** `backend/middleware/validateInput.js` (Task 08) — `validateRegister`, `validateLogin`, and `validateBookmarkUrl`, applied as exact-path middleware in `app.js` ahead of the relevant router mounts. `validateBookmarkUrl` only checks format when `url` is present; the "url or note required" rule remains owned by the Task 05 schema hook. `title` (Task 14 follow-up) has no dedicated validation — optional free-text field. **Relevant for Task 17:** `AddBookmarkForm.jsx` should mirror the "at least one of url/note" rule client-side (basic pre-submit check) since a submission with neither will otherwise round-trip to the server just to get a 400.
- **API Style:** REST (not GraphQL) under `/api/*` prefix.
- **Pagination:** `page`/`limit` query params on `GET /api/bookmarks`, default limit 12, response shape `{ data, total, page, pages }`, sorted newest-first by `createdAt`. Consumed by `BookmarkList.jsx`'s "Load more" (Task 14) and unaffected by Task 15's in-place update/delete (no refetch triggered). **Relevant for Task 17:** a newly created bookmark should be prepended to `BookmarkList.jsx`'s in-memory `bookmarks` array directly (consistent with the no-refetch pattern from Task 15/16), not trigger a full refetch of page 1.
- **Aggregation Route Pattern:** `getGrouped`/`getByTag` (Task 09) live in `bookmarkController.js` alongside CRUD handlers rather than a separate aggregation controller file, and their routes are registered in `bookmarks.js` *above* `GET /:id` to avoid Express's param-route matching swallowing them (`/grouped`, `/tags/:tag` would otherwise hit `:id` and produce a `CastError` → 404). `$match` on `user` requires manual `ObjectId` casting since aggregation pipelines don't auto-cast like normal query filters do.
- **Controller Response Shape:** `getBookmark`, `updateBookmark` (**confirmed flat in Task 16**, matching `getMe`), and (by established pattern) `createBookmark` all return a flat, unwrapped bookmark object — `res.status(200/201).json(bookmark)`. Only list-returning endpoints (`getBookmarks`, `getGrouped`, `getByTag`) wrap their array in `{ data: [...] }`. **Relevant for Task 17:** `AddBookmarkForm.jsx` should expect `POST /api/bookmarks` to return the created bookmark as a flat object (consistent with this now-fully-confirmed convention), not `{ data: bookmark }`.
- **Testing:** Jest + Supertest for backend integration tests (Task 10), run via `npm test` (`jest --runInBand`) against an in-memory MongoDB (`mongodb-memory-server`), not a dedicated `MONGODB_URI` test database. Gemini calls are mocked at the `aiService` module level in tests, never real. No frontend automated tests yet (deferred, see Open Questions — optional Task 21); Task 15's and Task 16's frontend work were only verified manually.
- **App/Server Split (Task 10):** `backend/app.js` exports the fully configured Express app (middleware, routes, `notFound`/`errorHandler`) with no DB connection or `listen()` call. `backend/server.js` is the only file that calls `validateEnv()`, `connectDB()`, and `app.listen()`. Anything needing the app without full bootstrap (tests, future scripts) requires `app.js` directly rather than `server.js`.
- **Test Database Strategy:** Backend integration tests use `mongodb-memory-server` (a fresh in-memory MongoDB instance per test run) rather than a real test database, so `setup.js` bypasses `connectDB()`/`config/db.js` entirely — no `MONGODB_URI` needed for tests.
- **Mongo Binary MD5 Check:** Disabled (`MONGOMS_MD5_CHECK=0`) in `backend/tests/setup.js` due to persistent checksum-mismatch failures on this dev machine (likely antivirus interference during binary download). Safe for local test runs; revisit if a CI environment (Task 19, deferred) shows the same issue or doesn't need the flag at all.
- **AI Mocking in Tests:** `aiService.generateSummaryAndTags` is mocked at the module level via `jest.mock('../services/aiService')` in `bookmarks.test.js`, rather than mocking the underlying `@google/generative-ai` SDK client — simpler since Task 07 already isolates all Gemini interaction behind that one function.
- **Frontend State:** React Context for auth (`AuthContext`, Task 12) and toast/notification state (`ToastContext`, Task 13); local component state/fetch calls for everything else — no Redux unless complexity demands it later. `BookmarkList.jsx` remains the single owner of the `bookmarks` array (fetch, pagination, in-place update/delete as of Task 15, and search/tag filter state as of Task 16).
- **Notifications:** One centralized toast system (`ToastContext` + `Toast.jsx`, Task 13) — `showToast(message, type, duration)` where `type` is `'success' | 'error' | 'info'` (convention, not enforced), auto-dismiss default 3.5s, multiple toasts stack, click-to-dismiss supported. Wired into: `Login.jsx` (error, on failed login), `Register.jsx` (error, on failed registration), `Home.jsx` (success, on logout), `BookmarkList.jsx` (error, on failed initial load or "Load more"), `EditBookmarkModal.jsx` and `BookmarkCard.jsx` (success/error on save/delete, Task 15). Every future task that performs a user-facing action should call `showToast(...)` on success and/or failure rather than inventing new inline feedback UI — **applies directly to Task 17's `AddBookmarkForm.jsx`.**
- **Folder/Tag Model:** Tags stored as an array of strings on the Bookmark document; "folders/collections" stored as a separate string field, aggregation done via MongoDB `$group` (implemented Task 09).
- **Filtering Model (Task 16):** Search + tag-pill filtering is implemented as derived/local view state inside `BookmarkList.jsx` — `searchTerm` and `activeTag` state, plus a `filteredBookmarks` array recomputed from `bookmarks` on every render (no memoization needed yet at current scale). Tag pills (`allTags`) are derived from the currently-loaded `bookmarks` array only, not fetched separately via `getByTag`/`getGrouped`. Search matches a lowercased `title + note + url` concatenation. Search and tag filters combine with AND logic. This is a pure client-side view layer with zero backend involvement — no new endpoints, no schema changes.
- **Bookmark Title Field (Task 14 follow-up):** `title` added to `Bookmark` schema — `String`, trimmed, `default: ''`, optional, user-typed only (not AI-generated, unlike `summary`/`tags`). Does not participate in the Task 05 "url or note required" cross-field validation rule and has no dedicated input validation. Wired through `createBookmark` and `updateBookmark` (assigned pre-`.save()`). `BookmarkCard.jsx` renders `title || url || 'Untitled bookmark'` as the heading, so bookmarks created before this change degrade gracefully. Editable via `EditBookmarkModal.jsx` as of Task 15. **Relevant for Task 17:** `AddBookmarkForm.jsx` should include an optional `title` input alongside `url`/`note`/`tags`/`collection` so newly created bookmarks aren't title-less by default.
- **XSS Note:** React escapes rendered text content by default; no `dangerouslySetInnerHTML` is used anywhere, so AI-generated summaries/tags (and user-typed `title`) are safe to render directly.
- **Repository:** Local git repo initialized in project root; connected to GitHub remote (`origin`). Task branches pushed individually (e.g. `feature/01-setup`) rather than committing directly to `main`.
- **Express Version:** Running Express 5.x — any future middleware must be checked for Express 5 compatibility before installing (see Task 03 deviation with `express-mongo-sanitize`; `express-rate-limit` v7 confirmed Express-5-compatible in Task 08).
- **bcrypt Library:** Using `bcryptjs` (pure JS) instead of `bcrypt` (native bindings) — avoids native compilation issues on Windows, same `hash`/`compare` API (see Task 04 deviation).
- **Cookie Testing Workflow:** When testing cookie-based auth with `curl.exe`, always pass `-c cookies.txt` (write) alongside `-b cookies.txt` (read) on any request whose response should update the saved cookie — otherwise `Set-Cookie` responses (e.g. from `/logout`) are silently discarded and stale cookies get reused. A `login.json`/`register.json` scratch file (never committed) holds plaintext test credentials so curl has a body to send without fighting PowerShell quote-escaping.
- **PowerShell curl Quoting:** `curl.exe` in PowerShell mishandles `-d "{\"key\":\"value\"}"` style JSON bodies (mangles quotes/args). Preferred workaround: write JSON to a file (`'{"key":"value"}' | Out-File body.json -Encoding utf8`) and pass `-d "@body.json"` instead of inline JSON strings. Use `-Encoding utf8` explicitly — older PowerShell defaults to UTF-16, which can corrupt JSON for curl.
- **Bookmark Validation Pattern:** "At least one of X or Y required" cross-field validation is done via a `pre('validate')` schema hook + `this.invalidate()`, not per-field `required` functions — established in `Bookmark.js` (Task 05) as the pattern for any future conditional-field validation. Hook must follow the async/no-`next` style above.
- **Bookmark Defaults:** `collection` defaults to `'Uncategorized'` rather than being left empty, so every bookmark has a folder grouping out of the box (Task 05 deviation).
- **Route-Specific Middleware Without Editing Route Files:** When a task's target files list `server.js`/`app.js` but not the relevant `routes/*.js` file, exact-path `app.METHOD(path, ...middleware)` registered before the router's `app.use(prefix, router)` mount achieves per-route middleware (validation, rate limiting) without touching the router file — the request falls through via `next()` into the existing router untouched (Task 08 pattern; reusable for future tasks with the same constraint).
- **Frontend Build Tool:** Vite (`react` template, ESLint as linter) — chosen over CRA for speed and current standard practice. Resolves the Task 01 open question of whether `frontend/` had a real scaffold; it didn't, so Task 11 created one (Task 11).
- **Frontend HTTP Client:** Native `fetch` via a hand-written `apiClient` wrapper (`frontend/src/api/client.js`), not axios — avoids an extra dependency, `credentials: 'include'` covers the cookie requirement directly. Exports `get`/`post`/`put`/`delete`, all routed through a shared `request()` helper that sets `credentials: 'include'`, JSON-stringifies bodies, and throws on non-OK responses (Task 11). **As of Task 15:** `request()` also attaches `err.status = res.status` to every thrown error before throwing. Callers can branch on `err.status` (e.g. `404`, `409`, `429`) instead of string-matching `err.message` — **use this convention in `AddBookmarkForm.jsx` for Task 17** (e.g. `err.status === 429` for the `aiLimiter` cap).
- **Frontend Routing:** `react-router-dom` with `BrowserRouter`/`Routes` in `App.jsx` (Task 11), extended in Task 12 with `/login`, `/register`, and a `ProtectedRoute`-guarded `/` route wrapped in `AuthProvider`, further wrapped in `ToastProvider` (Task 13). No new routes anticipated for Task 17 — `AddBookmarkForm.jsx` will live inside the existing `/`-route UI (likely rendered from `Home.jsx`, above or below `BookmarkList.jsx`), not a separate page.
- **Frontend Env Vars:** `frontend/.env` uses the `VITE_` prefix (Vite-only requirement to expose vars to client code) — current var is `VITE_API_BASE_URL` (Task 11).
- **`apiClient` Response Unwrapping:** `apiClient` methods return raw parsed JSON with no automatic unwrapping. Auth endpoints (`/me`, `/login`, `/register` — Task 04) return flat user objects, so `AuthContext` (Task 12) consumes them directly with no unwrapping needed. Endpoints that wrap array data in `{ data: [...] }` (paginated `GET /api/bookmarks`, `getGrouped`, `getByTag`) require callers to read `.data` explicitly. `BookmarkList.jsx` unwraps `res.data` locally (Task 14). `EditBookmarkModal.jsx` (Task 15) and (planned) `AddBookmarkForm.jsx` (Task 17) both consume flat, unwrapped single-bookmark responses directly — **this convention is now fully confirmed, not assumed, as of Task 16.**
- **Backend Env Loading Fixed (Task 11 deviation):** `backend/server.js` must call `require('dotenv').config()` as its first line, before `validateEnv()`. This was lost at some point (likely the Task 10 `app.js`/`server.js` split) and caused a startup crash. `config/env.js` now exports `{ validateEnv }` (named export) to match the destructured import in `server.js` — this is now the canonical export style for `config/env.js`; keep it in mind if `env.js` is touched again.
- **Frontend Auth State:** `frontend/src/context/AuthContext.jsx` (Task 12) exports `AuthProvider` (wraps app, holds `user`/`loading` state, checks `GET /api/auth/me` on mount) and `useAuth()` hook exposing `{ user, loading, login, register, logout }`. `login`/`register`/`logout` call the corresponding backend endpoints and update local `user` state directly from the response — no separate refetch of `/me` after login/register.
- **Frontend Route Guarding:** `frontend/src/components/ProtectedRoute.jsx` (Task 12) is a layout-style route component using `react-router-dom`'s `<Outlet />`, nested as a wrapping `<Route>` around any route that requires auth. Shows a loading state while `AuthContext`'s initial `/me` check is in flight, then redirects to `/login` via `<Navigate replace>` if no user, otherwise renders the child route. `Home.jsx`, `BookmarkList.jsx`, `SearchBar.jsx`/`TagPills.jsx` (Task 16), and the edit/delete UI on `BookmarkCard.jsx` (Task 15) all already live inside this guard — Task 17's `AddBookmarkForm.jsx` will too, needing no additional guarding.
- **Page Component Location:** All route-level page components (`Login.jsx`, `Register.jsx`, `Home.jsx`) live in `frontend/src/pages/`. Non-page, reusable UI pieces (`Toast.jsx`, `BookmarkCard.jsx`, `BookmarkList.jsx`, `EditBookmarkModal.jsx` — Task 15, `SearchBar.jsx`/`TagPills.jsx` — Task 16) live in `frontend/src/components/` instead. Task 17's `AddBookmarkForm.jsx` follows this same convention and belongs in `frontend/src/components/`.
- **Bookmark List Component Structure:** `BookmarkList.jsx` owns fetch/pagination state (`bookmarks`, `page`, `pages`, `loading`, `loadingMore`), edit/delete handlers (`handleUpdate`, `handleDelete` — Task 15), and search/tag filter state (`searchTerm`, `activeTag`, derived `allTags`/`filteredBookmarks` — Task 16), rendering one `BookmarkCard` per item in `filteredBookmarks` (not raw `bookmarks`). **Relevant for Task 17:** the natural integration point for a newly created bookmark is a new handler in `BookmarkList.jsx` (e.g. `handleCreate(newBookmark)` that prepends to `bookmarks`), consistent with how `handleUpdate`/`handleDelete` already mutate local state in place — decide during Task 17 whether `AddBookmarkForm.jsx` lives inside/near `BookmarkList.jsx` or is lifted to `Home.jsx` with a callback passed down, since it needs to affect `BookmarkList.jsx`'s state from outside it.
- **Delete Confirmation Pattern (Task 15):** Delete uses native `window.confirm()` rather than a custom in-app modal — resolves the Task 15 open design question. `EditBookmarkModal.jsx`'s modal component/styling is not reused for delete; delete stays a simple synchronous browser-native interaction inside `BookmarkCard.jsx`'s `handleDelete`.
- **Error Status Codes on the Frontend (Task 15):** `apiClient`'s `request()` now sets `err.status = res.status` on every thrown error. Established usage pattern: check `err.status === 404` for "resource no longer exists" (already-deleted/edited-elsewhere race conditions) before falling back to a generic error toast with `err.message`. Any future component doing mutating API calls (create/update/delete) should follow this pattern rather than string-matching `err.message` — **applies to `AddBookmarkForm.jsx`'s 429 handling in Task 17.**
