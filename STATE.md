## Key Architectural Decisions
- **AI Provider:** Google Gemini API, accessed via its official SDK from the backend only (never exposed to frontend).
- **AI Model Choice:** Using `gemini-3.5-flash-lite` — the free tier caps full Flash models (`gemini-3.5-flash`, `gemini-3.6-flash`, `gemini-2.5-flash`) at 20 requests/day, unusable for dev iteration, while Flash-Lite gives 500/day and 15 RPM. Flash-Lite is also the right fit for the task itself (short extraction/classification, not long-form reasoning), not just the cheaper option (Task 07).
- **AI Failure Handling:** `aiService.generateSummaryAndTags` never throws — on any Gemini error, malformed response, or fetch failure it returns `{ summary: null, tags: [] }` so bookmark creation always succeeds even if the AI call fails, times out, or the source page can't be fetched (Task 07). Task 08 confirmed this path also covers rate-limit/timeout cases without additional code.
- **Bookmark Content Source for AI:** Priority order is fetched page text (via `urlFetcher.fetchPageText`) → user-submitted `note` → raw `url` string as a last resort. Page fetches are capped at 6 seconds and 6000 characters to bound latency and token cost (Task 07).
- **Tag Merging:** `createBookmark` merges user-submitted tags with AI-generated tags rather than one overriding the other, deduped case-insensitively with user-typed casing taking priority on collision. Near-duplicate tags that aren't exact string matches (e.g. "Node.js" vs "NodeJS") are NOT currently caught — deferred, see Open Questions (Task 07).
- **Database:** MongoDB with Mongoose for schema/validation. Bookmark schema indexes `user` and compound-indexes `{ user, tags }` for aggregation performance — this index is what Task 09's `$group` queries will rely on.
- **DB Connection Pattern:** `backend/config/db.js` exports a single async `connectDB()` function, called once at server bootstrap in `server.js`; connection failure exits the process rather than allowing the server to start in a broken state.
- **Auth:** JWT-based sessions. Token issued on login, stored in an httpOnly, `SameSite=Lax` cookie (not localStorage) to reduce XSS exposure. Passwords hashed with `bcryptjs`, salt rounds ≥10. Token expiry set to 7 days. Cookie/JWT logic centralized in `backend/utils/generateToken.js` (`generateToken`, `setTokenCookie`, `clearTokenCookie`) rather than duplicated per-route.
- **Password Field Handling:** `User.password` uses `select: false` in the schema so it's excluded from query results by default; `authController.login` explicitly opts in with `.select('+password')` only where needed.
- **Authorization Pattern:** Every bookmark query filters by ownership in a single combined Mongo filter (e.g. `{ _id, user: req.user.id }`), set via `auth.js` middleware — no bookmark route is ever unprotected, and no route queries `Bookmark` without that scope. Task 09's aggregation routes must scope the `$match` stage by `user: req.user.id` for the same reason (this is Task 09's core "Done When" requirement).
- **Not-Found vs Forbidden:** Bookmark routes return `404` (not `403`) for both "doesn't exist" and "exists but belongs to another user," and also for malformed ObjectId `CastError`s — all three cases are indistinguishable to the caller, preventing existence/ownership leaks (Task 06).
- **Mongoose Hook Style:** `pre('validate')`/`pre('save')` hooks are written as `async function () {...}` with no `next` parameter — never mix an `async` hook signature with an explicit `next()` call, since Mongoose only supplies `next` to non-async hooks and calling it on an async hook throws `TypeError: next is not a function` (Task 06 deviation, fixing the Task 05 hook).
- **Mutating Updates Use `.save()`:** `updateBookmark` fetches the document then calls `.save()` rather than `findOneAndUpdate`, so schema-level `pre('validate')` hooks (e.g. the url/note cross-field rule) still run on edits, not just on creation.
- **Security Middleware:** `helmet` for headers, `morgan` for request logging, and a custom in-place sanitizer (see Task 03 deviation) against NoSQL injection — all applied at server bootstrap (Task 03), before any feature routes exist.
- **CORS:** Configured early for local dev (`CLIENT_ORIGIN`, `credentials: true`), locked to the production frontend origin only at deploy time (Task 18).
- **Rate Limiting:** Implemented in Task 08. `authLimiter` (15 min / max 10 / only failed attempts count) applied to `POST /api/auth/login`; `aiLimiter` (1 hour / max 20) applied to `POST /api/bookmarks` only. Both wired as exact-path `app.post(...)` middleware in `server.js`, registered before the corresponding router mount, rather than inside `routes/auth.js`/`routes/bookmarks.js`.
- **Error Handling:** Centralized in `backend/middleware/errorHandler.js` (Task 08) — `notFound` + `errorHandler`, mounted last in `server.js`. Existing Task 06/07 controllers still catch and respond locally per-handler (not refactored to `next(err)`); `errorHandler.js` currently acts as a safety net for anything uncaught or thrown outside those try/catch blocks, not the primary path yet.
- **Input Validation:** `backend/middleware/validateInput.js` (Task 08) — `validateRegister`, `validateLogin`, and `validateBookmarkUrl`, applied as exact-path middleware in `server.js` ahead of the relevant router mounts. `validateBookmarkUrl` only checks format when `url` is present; the "url or note required" rule remains owned by the Task 05 schema hook.
- **API Style:** REST (not GraphQL) under `/api/*` prefix.
- **Pagination:** `page`/`limit` query params on `GET /api/bookmarks`, default limit 12, response shape `{ data, total, page, pages }`, sorted newest-first by `createdAt`.
- **Testing:** Jest + Supertest for backend integration tests (Task 10), run against a separate test DB; Gemini calls are mocked in tests, never real. Frontend component testing is optional (Task 21).
- **Frontend State:** React Context for auth and toast/notification state; local component state/fetch calls for everything else — no Redux unless complexity demands it later.
- **Notifications:** One centralized toast system (Task 13), built before any feature UI, reused by every later interaction (auth errors, add/edit/delete).
- **Folder/Tag Model:** Tags stored as an array of strings on the Bookmark document; "folders/collections" stored as a separate string field, aggregation done via MongoDB `$group`. This is the direct subject of Task 09.
- **XSS Note:** React escapes rendered text content by default; no `dangerouslySetInnerHTML` is used anywhere, so AI-generated summaries/tags are safe to render directly.
- **Repository:** Local git repo initialized in project root; connected to GitHub remote (`origin`). Task branches pushed individually (e.g. `feature/01-setup`) rather than committing directly to `main`.
- **Express Version:** Running Express 5.x — any future middleware must be checked for Express 5 compatibility before installing (see Task 03 deviation with `express-mongo-sanitize`; `express-rate-limit` v7 confirmed Express-5-compatible in Task 08).
- **bcrypt Library:** Using `bcryptjs` (pure JS) instead of `bcrypt` (native bindings) — avoids native compilation issues on Windows, same `hash`/`compare` API (see Task 04 deviation).
- **Cookie Testing Workflow:** When testing cookie-based auth with `curl.exe`, always pass `-c cookies.txt` (write) alongside `-b cookies.txt` (read) on any request whose response should update the saved cookie — otherwise `Set-Cookie` responses (e.g. from `/logout`) are silently discarded and stale cookies get reused. A `login.json`/`register.json` scratch file (never committed) holds plaintext test credentials so curl has a body to send without fighting PowerShell quote-escaping.
- **PowerShell curl Quoting:** `curl.exe` in PowerShell mishandles `-d "{\"key\":\"value\"}"` style JSON bodies (mangles quotes/args). Preferred workaround: write JSON to a file (`'{"key":"value"}' | Out-File body.json -Encoding utf8`) and pass `-d "@body.json"` instead of inline JSON strings. Use `-Encoding utf8` explicitly — older PowerShell defaults to UTF-16, which can corrupt JSON for curl.
- **Bookmark Validation Pattern:** "At least one of X or Y required" cross-field validation is done via a `pre('validate')` schema hook + `this.invalidate()`, not per-field `required` functions — established in `Bookmark.js` (Task 05) as the pattern for any future conditional-field validation. Hook must follow the async/no-`next` style above.
- **Bookmark Defaults:** `collection` defaults to `'Uncategorized'` rather than being left empty, so every bookmark has a folder grouping out of the box (Task 05 deviation).
- **Route-Specific Middleware Without Editing Route Files:** When a task's target files list `server.js` but not the relevant `routes/*.js` file, exact-path `app.METHOD(path, ...middleware)` registered in `server.js` *before* the router's `app.use(prefix, router)` mount achieves per-route middleware (validation, rate limiting) without touching the router file — the request falls through via `next()` into the existing router untouched (Task 08 pattern; reusable for future tasks with the same constraint).
